# 自計化レビュー v4.4 設計書：BS・PL・仕訳帳をつなぐレビュー

作成日：2026年10月9日。調査基準日：2026年10月9日（日本時間）。

## 0. この文書について

- **対象**：利用者の最新版 **v4.3（版表示 4.3.0、2,108,918バイト、45スクリプトブロック）** を土台にした次の版（仮称 v4.4）の設計です。出発点は「BS_PLレビュー_調査と実装設計_20261009.md」（以下「調査メモ」）です。
- **範囲**：調査結果、優先順位付きの機能仕様、段階的な実装案、検証計画まで。**アプリの変更・公開・freeeへの書込みはしていません**。実装は、別途指定された段階だけを行います。
- **根拠の書き方**：v4.3 のコードは `B/NN:行` で示します（v4.3 を `<script>` ごとに分けた NN 番目のブロックの物理行）。一次資料は `S番号`（調査メモの番号を引き継ぐ）で示し、一覧と確認日は §5 にまとめます。
- **アプリ独自の設定と法令を分けます**：「5万円かつ30%」「3か月動かない」などの数値は、**確認候補を絞るためのアプリ独自の目安**です。会計基準や税法がその数値を定めているわけではありません。
- **説明の4段**：本書のすべての機能は、表示を次の4つに分けます。
  1. **記録上の事実**：CSVにそのまま書かれていること、またはその集計
  2. **原因の候補**：事実から考えられる可能性（複数を並べ、1つを正解にしない）
  3. **不足資料**：判断を進めるのに必要な、CSVにない情報
  4. **次の行動**：誰が、何を確認するか
- **確認の4区分**：確認の状態を1つのチェックにまとめず、次の4つを別々の項目として持ちます。
  - 帳簿内照合（帳票と仕訳が合うか）
  - 外部資料の確認（通帳・請求書などと合うか）
  - 人による確認（用途・例外の根拠を確認したか）
  - 利用者の対応状態（未対応・確認中・修正済み・完了など）
- **機密**：利用者の実CSVは、手元で読み取り専用で扱いました。本書には件数と性質だけを書き、取引先名などの中身は載せていません。

### 1.1 調べた方法

| 対象 | 方法 | 結果の置き場所 |

**確認できなかったこと**
- 利用者の**実際の仕訳帳CSV**は今回渡されていません。そのため、実データでの仕訳と帳票の突合は試していません。
- 次の操作は試していません：印刷、推移グラフ、ドラッグ＆ドロップ、11ファイル以上の一括読込、12MBを超えるCSV、スマホ幅、対象期間の変更による候補IDの変化（コードで確認しただけ）。「修正したので再確認」から完了にする流れ。
- e-Gov では、平成28年改正法附則（インボイス経過措置の条文）の現行版を取得できませんでした。インボイス関係は国税庁Q&Aに示された根拠条項に基づいていて、**条文本文での検証はしていません**。
- freee 仕訳帳CSVに、税額やインボイス関連の列がどんな名前で出るかは、一次資料では確かめられていません。

### 1.3 v4.3 で見つかった、設計で手当てが必要な問題

いずれも、今回の実行か、コードを読んで確かめたものです。

| 番号 | 問題 | 確認方法 | 影響 |
|---|---|---|---|
| R1 | 候補IDが、設定・文言・資料で変わる。ID には理由文、金額、対象期間、重要性、`session.financial` の全項目が入る（`B/00:205-211`） | 実行：「照合条件の確認」（`comparisonConfirmed`）をONにすると、66件のIDのうち残ったのは0件。重要性を1円変えても0件 | 完了記録は消えないが「以前の候補」に回り、同じ論点が新しい受付として二重に並ぶ |
| R2 | 同じCSVを読み直すだけで、完了記録が全件「再検証」に戻る。原因は3つの経路にある。(1) 読込のたびに `invalidateChecks()` が呼ばれる（`B/43:359`）。この関数は全件を無効にし、「照合条件の確認」もOFFにする（`B/43:93`）。呼び出し元はほかにも10か所ある（`B/43:217,397,402,405,411,422,423,436,439,440`）。(2) 当期の仕訳帳を読むと「網羅性の確認」（`project.complete`）がOFFになる（`B/43:359`）。(3) 対応ワークフローは、会社全体のトークン（全資料と設定から作る。`B/19:56-66`）が変わると、完了を再検証として表示する（`B/19:121-123`）。内容が同じなら無効にしない仕組み（`B/19:61`）は使われていない | 実行 | 完了済みの確認をやり直すことになる。チェックシートの完了も未着手に戻る |
| R3 | CSVの中身が変わると、記録を付けた候補のIDがすべて変わる。対象の行に触れていない候補も変わる | 実行：2行を変えると、記録を付けた3件のIDがすべて変わった | 古い記録が「現在の候補に未適用」で残り、新しい同じ候補と二重に並ぶ |
| R4 | 同じバックアップを2回復元すると会社が重複する。重複の判定が会社データの完全一致（`B/38:43-48`）で、復元後に開くと再計算で内容が変わるため | 実行 | 会社一覧が「(復元 2)」で増える |
| R5 | 対象期間の初期値が決算月と関係なく 2026-01〜06。期間外の行は取込時に警告されない | 実行：12月決算でも3月決算でも同じ。架空の仕訳帳で69行が期間外になった | 気づかないまま一部の月だけをレビューする |
| R6 | 税制の日付が `LAW` に直書きで、成立・施行の状態、確認日、対象者、適用終了日、例外を持たない。少額減価償却資産の40万円に取得期限（2029-03-31）の判定がない（`B/04:153`）。インボイスの割合を「取引日と合っていない」と言い切っている（`B/04:190-198`） | コード | 期限切れのルールや、確定できない判定を断定してしまう |
| R7 | 根拠の「CSV行」が論理レコード番号で、セル内改行がある場合は物理行と一致しない（`B/00:109,142`） | コード | 元CSVを開いたときに、指している行が見つからない |
| R8 | Worker 用のエンジン文字列（`B/36`）を手作業で同期している | コード | 片方だけ直すと、5,000行以上の会社だけ違う結果になる |
| R9 | 候補ごとのハッシュ計算が重い。根拠行の全項目と科目の帳票行全体を毎回文字列にしている（`B/00:165`） | 実行：仕訳帳を25倍（約7,250行）にすると読込18.4秒、再チェック6.1秒、保存データ15.6MB | 大きな会社で遅く、保存が重い |
| R10 | Claude版v3.9 にあって v4.3 にない機能：決算月からの期間設定、過去仕訳からの取引先別期首の推定、回収・支払の停滞、タグ別BSの仮勘定の停滞と負の残高 | コード | 本書の F01・F05・F06 で、原則に沿う形で戻す（推定を確定値として扱わない） |

### 1.4 守るべきデータの形

v4.4 では次の形を変えません。新しいデータは別の名前で追加します。

- **Workspace**（IndexedDB `ledger-atelier-review`、ストア `sessions`、キー `workspace`）
  - `{kind:'ledger-atelier-workspace', schema:2, companies:[{id, name, entityType, owner, closingMonth, note, archived, createdAt, summary, session}], activeId, updatedAt, preferences}`（`B/38:9,18,23-33`）
  - `entityType` は `''`（未設定）・`corp`・`individual`。`preferences` は検証で `theme` だけが残る（`B/38:25`）
- **Session**（`schema:1`）
  - `project{name, type, start, end, large, variance, complete}`。`type` は常に individual か corp のどちらかで、初期値は individual（`B/00:281,294`）。**未設定を表せない**ため、法人／個人の判定には使わない（会社の `entityType` を使う。§3.4）
  - `datasets`：current、prior、unregistered、balances、aging、monthlyPL、monthlyBS、priorPL、priorBS
    - 帳票の行は `reportViewDimension`（total／party／item／department）、`tagDimension`、`tagValue` で切り口を区別する（`B/07`）
  - `financial`、`imports[]`、`decisions`、`manual`、`history`、`teacher`、`updatedAt`、`demo`
  - `responseWorkflow{schema, updatedAt, finalReview, tasks}`（`B/19:11-51`）
  - Claude版v3.9 から復元したときだけ `tagReports` と `claudeBackupMigration` がある（`B/06`）
- **許可リストの検証**：`E.validateSession` は既知のキーだけを残します（`B/00:292`）。起動のたびに通るため、**登録していない新しいキーは再読込で消えます**（実行で確認）。新しい保存項目は、必ずこの検証に登録します。
- **対応記録の検証は厳しい**：履歴の事象は6種類（saved・retest・reopened・invalidated・completed・signoff）に限られます（`B/19:25`）。`findingSnapshot` の項目も許可リストで、その `id` は記録のキーと一致しなければなりません（`B/19:28-32,39`）。起動時の検証でエラーになると、全社のデータが保存されないまま止まります（`B/43:125-127`）。**既存の構造には、v4.3 の検証を通る値だけを書きます。**
- **既存の「同じ論点」の鍵**：対応ワークフローには、候補の種類と文脈（または科目と月）から作る `anchor()` があります（`B/19:98`）。新しい論点キーは、これを土台にします（§3.5）。
- **バックアップ**
  - 1社分：`{kind:'ledger-atelier-company', schema:1, company, kubunChecker?}`

#### 1.5.4 BS・PL・仕訳帳の突合

| 確認 | 計算・条件 | 混ぜないもの | 誤判定を防ぐ扱い |
|---|---|---|---|
| BS接続 | 前月末＋当月の仕訳増減＝当月末（帳票） | BSの月末残高と、当月の増減額 | 控除科目・負の残高・期首仕訳は別扱い。期首を逆算した場合は「逆算値」と表示し、資料の値と区別する |
| PL照合 | 科目×月の仕訳集計＝単月PL | 単月と累計 | 累計の帳票は、前月の累計がそろう場合だけ差分で単月にし、元の形式を残す |
| 内訳の照合 | タグ別の内訳の合計＝科目合計（未選択を含む） | 取引先・品目・部門の各切り口（同じ仕訳を足し合わせない） | 合わない差は「内訳不明」に残し、取引先に配分しない |
| タグ | 対象科目と同じ側のタグ | 反対側のタグ | 空欄を反対側から補わない。共通列の取引先だけは両側に使う |
| 期首内訳 | BS×取引先などの帳票の「期首」 | 推計値と確定値 | 科目合計から取引先へ配分して作らない |
| 集計条件 | 会社・期間・円／千円・税込／税抜・決算整理の範囲 | 千円の帳票と円の仕訳 | 千円の丸め幅（内訳の件数×1,000円まで）を超えない差でも「完全一致」とは表示しない |
| 利益と純資産 | 当期利益、増資・配当、事業主貸借を分けてつなぐ | 月次帳票が自動で表示する当期利益と締めの仕訳 | 二重に数えない |

#### 1.5.5 法人と個人の区別

| 確認点 | 法人 | 個人事業主 |
|---|---|---|
| 対象期間 | 実際の事業年度・課税期間 | 所得税は原則として暦年。開業・廃業の年に注意 |
| 事業と本人の資金 | 会社と役員・株主は別。役員への貸付・借入、立替、経済的利益（S19、S20） | 事業主貸・事業主借・元入金。生活費や所得税の支払は経費にしない（S08） |
| 本人への資金移動 | 配当・資本取引・役員給与を分けて判定 | 事業主の引出しは「事業資金の減少」と説明し、経費の増加とは言わない |
| 家族への支払 | 給与の実態を確認 | 原則（必要経費不算入）と、専従者給与・控除の要件を分ける（S08、S37） |
| 減価償却・少額資産 | 損金経理と償却限度（S11）。少額特例は中小企業者等で、損金経理と別表16(7)（S09） | 所得税の償却計算。少額特例は一定の青色申告者（S10） |
| 預金利息 | 法人の収益（源泉税は税額控除の論点） | 利子所得。事業の売上・雑収入に一律に入れない（S21） |
| 税金 | 法人税等・事業税・地方税・防衛特別法人税・消費税を区別（S22、S45） | 所得税・住民税は経費にならない。事業税・消費税を区別（S08） |
| 消費税の特例 | 2割特例（課税期間による） | 2割特例に加えて、3割特例（個人だけ。2027・2028年分） |

**法人か個人か、決算月、消費税の方式（本則・簡易・2割・3割）、税込／税抜、会計の枠組みは、会社ごとの設定から取ります。** 未設定のときは両方を候補として示し、結論は出しません。科目名（例：「事業主貸」がある）から法人・個人を決めません。

#### 1.5.7 判定に使わない情報

- **改正案・要望**：消費税率引下げ（S39）、交際費特例の延長要望（令和9年度税制改正要望）など。ルール表に `status: 'proposal'` として持つだけにし、判定には使いません。画面では「未成立・確認日」つきの情報欄にだけ出します。
- **統計**：業種別の経営指標（S32）、売上債権回転期間の統計（S31）は、定義の参考にとどめます。「同業平均より低い」を誤りの基準にしません。
- **ページの更新日**：法令の施行日や、会社の適用年度とは別のものです。同じものとして扱いません。

### 1.6 基本資料と追加資料

- **基本資料**：当期・前期の仕訳帳と、当期の月次BS・PL です。月次BS・PL は、表示するタグ＝なし・取引先・品目・部門 のどれでも読めます。
  - 前期の月次BS・PL は、前期の仕訳帳が完全で比較できるなら必須にしません。
- **実際にCSVにある列だけを使います。** freee 仕訳帳CSVでv4.3が読む主な列：取引日、仕訳番号、借方／貸方の勘定科目・金額・税区分・取引先・品目・部門・メモタグ・セグメント、摘要、管理番号、決算整理仕訳、作成日時など（`B/00:63-74`）。
  - 税額・インボイス関連の列は読んでいません。列があれば、その論点の確認にだけ使う設計にします。
- **追加資料は、その論点の確認に必要になった時だけ求めます。** 機能ごとに「必要な場合だけ求める資料」を §2 に書きます。資料がなくても、独立してできる照合や候補の抽出は進めます。
- **一度確認した会社の情報は使い回します。** 対象は、法人／個人、決算月、税込／税抜、消費税の方式、会計の枠組み、規模の要件です。結論が変わる論点に出会ったときだけ、一度質問します。

## 2. 優先順位付きの機能仕様

### 2.0 すべての機能が使う共通の仕組み

各機能の前提になるため、P0 の段階で作ります。

| 番号 | 仕組み | 内容 |
|---|---|---|
| C1 | **論点キー（issueKey）** | 候補ごとに、設定・文言・金額・ファイル名に左右されないキーを持たせる。土台は v4.3 の `anchor()`（`B/19:98`）で、これに「理由の種類（タイトルの雛形の番号）」と、取引単位の候補では「仕訳番号の集合」を足す。形：`v44:ルールIDまたは候補の種類｜帳票または仕訳｜科目（正規化）｜月または期間｜切り口｜タグ（正規化）｜仕訳番号の集合`。既存の候補ID（`B/00:211`）はそのまま残し、キーを横に足す（R1・R3 の対策。詳しくは F00）。**同じ論点キーに今回の候補が2件以上ある、または過去の記録が2件以上あるときは、自動で引き継がず「手で対応づけが必要」と表示する** |
| C2 | **根拠の指紋（evidenceHash）** | 候補の根拠になった行を、内容で要約したもの。仕訳は「仕訳番号＋日付＋科目＋側＋金額＋税区分＋対象側のタグ」、帳票は「種類＋科目＋月＋切り口＋タグ＋金額」で作る。**取込の指紋（ファイル全体のハッシュ）、論理行・物理行、ファイル名、取込の識別子、設定値は入れない**（ファイルのどこかが変わるだけで全部の指紋が変わるのを防ぐ。行番号は表示用に別に持つ）。「同じ論点で、根拠の中身も同じか」を判断するのに使う |
| C2b | **判断の前提の指紋（basisHash）** | その候補の判定に使ったルールのIDと版、関係する会社の事実（法人／個人、決算月、消費税の方式、税込／税抜、青色申告か、会計の枠組み）、候補を絞る目安の値で作る。根拠の中身が同じでも前提が変われば、記録を自動では引き継がない |
| C3 | **確認の4区分** | 帳簿内照合（自動）、外部資料の確認（人が記録）、人による確認（人が記録）、利用者の対応状態（既存の3系統の状態）を別の項目として持つ。どれか1つが済んでも、他を「済み」にしない。人が記録する2つは論点キーごとに持ち、論点キーのない候補は候補IDごとに持つ。根拠か前提が変わったら、2つの記録は写し（§3.4 の snapshots）に残して「未確認」に戻す |
| C4 | **説明テンプレート** | `{事実, 原因の候補[], 不足資料[], 次の行動[], 根拠参照[], 比較金額, 対象月, ルール参照[]}` を組み立て、「事実 → 原因の候補 → 不足資料 → 次の行動」の順に表示する。文はローカルの日本語の定型文から作る。外部AIや有料APIは使わない |
| C5 | **共有の索引** | 会社×データ版ごとに、次の索引を一度だけ作って使い回す：科目×月×側（借方／貸方）×タグ×仕訳番号、仕訳番号→全行、現預金の行、帳票の科目×月×切り口。科目数や取引先数に比例して全仕訳を読み直さない |
| C6 | **制度ルール表** | 版つきの静的な表（§1.5.1 の行）。各行に、法的段階、判定に使う日付の種類、有効期間、対象者、要件、例外、出典、確認日を持つ。改正案は判定に使わない（F02） |

**候補を絞る目安（アプリ独自。法令の基準ではない）**
- 変動の目安：比較できる月について「増減5万円以上、かつ30%以上」から始め、会社の重要性（`project.large`）と科目に合わせて調整できるようにする。
- 「動いていない」の目安：3か月（F05・F06）。
- 制度の境界の目安：境界の日の前後30日（F02）。
- ルールの確認日から180日：「制度の再確認が必要」の**お知らせ**を出すだけで、判定には使わない（F02）。
- 前月が0円、負の値、ごく小さな金額のときは割合を使わず、金額と件数だけを示す。
- 重大な照合の不一致や、制度の境界に当たる候補は、この目安とは関係なく出す。

### F00 対応記録の保全と引継ぎ（P0）

**v4.3 との関係**：対応ワークフロー（`B/19`）、`decisions`、チェックシート（`manual`）はそのまま使います。次の3点を直します。
- 候補IDが変わると記録が二重に並ぶ（R1・R3）
- 読み直しで完了が全件戻る（R2）
- 2回の復元で会社が重複する（R4）

**優先の理由**：完了記録を再分析で消したり、未対応に戻したりしないことが、この設計の前提だからです。

| 項目 | 内容 |
|---|---|

  - 仕訳を2行変えて読み直すと、影響する論点だけが「データ更新による再確認」になり、旧記録が残る。

  - v4.3・Claude版v3.9・v3.2統合版のバックアップが、これまでどおり復元できる。

### F01 資料の範囲と、BS・PL・仕訳の整合性（P0）

**v4.3 との関係**：ほとんどの照合は既にあります（借貸の差、BS接続、PL照合、帳票内の検算、読込月の網羅性、内訳の照合、基盤が未確定なら後ろを止める仕組み）。足りないものだけを補います。
- 対象期間の提案と、期間外の行の警告（R5）
- 物理行の参照（R7）
- 税込／税抜の方式の確認
- 期首・決算整理の区別の表示
- 照合の結果を1枚にまとめた「整合性の表」
- 累計表示のPLの単月化（任意）：v4.3 は累計表示のPLを理由を示して拒否します（`B/03:107`）。この動作を初期値として残します。単月にするのは、帳票の期間が事業年度の最初の月から始まり、すべての月がそろう場合だけです。単月にしても元の形式（累計）を保持し、「累計から計算」と表示します。

**「差が説明済み」の定義**（F03・F04 で使う）
- 差額が千円の丸めの幅に収まる場合
- 利用者が、その科目×月の差について原因を記録した場合（確認の4区分の「人による確認」）

それ以外の差は「未解明」です。

**優先の理由**：照合の前に原因を説明すると、誤った説明になるためです。

| 項目 | 内容 |
|---|---|
| ①検出条件 | (1) 範囲：会社名（帳票の事業者名）、期間（帳票のタイトルと見出し）、単位（円／千円）、単月／累計、データの種類（当期・前期）が設定と合うか。仕訳の月別件数（`imports[].monthCounts`）に0件の月がないか。対象期間の外にある行の数。<br>(2) 照合：借方合計＝貸方合計（仕訳のまとまりごと）。BSの科目ごとに、前月末＋当月の仕訳増減＝当月末。PLの科目×月で、仕訳の集計＝単月PL。資産＝負債＋純資産。BSの当期利益とPL累計のつながり。タグ別の内訳の合計＝科目合計。<br>(3) 方式：仕訳の税区分と「消費税経理処理方法」の列から推定される方式と、会社の設定が合うか。<br>(4) 期首・決算整理：開始残高の仕訳、決算整理仕訳（`isAdjustment`）を別に集計する。<br>**判定不能**：前月末の帳票がない最初の月、期首の資料がない場合、千円の帳票と円の仕訳、方式が未設定でCSVからも分からない場合。それぞれ理由を付けて「判定保留」にする |
| ②表示する根拠 | 「整合性の表」に照合ごとの行を置く：照合名、計算式、左辺と右辺の金額、差額、状態（一致／差あり／判定保留＋理由）、根拠（元CSVのファイル・物理行・仕訳番号）。差は「未解明差額」として、どの科目にも配分せずに残す。期首を式から逆算した場合は「逆算値（仕訳が完全な場合だけ成り立つ）」と表示し、資料の値と区別する |
| ③初心者への説明 | 「3月の売掛金は、帳票の残高と、前月末に仕訳の増減を足した額が12,000円合いません。差の原因が分かるまで、売掛金の変動の説明は『保留』にしています。」／「10月〜12月は仕訳帳がまだ読み込まれていません。この3か月は変動の判定をしていません。」 |
| ④次の行動 | 差のある科目×月について、根拠の仕訳を開く。出力期間とフィルターを確かめ、必要な範囲だけを再出力して読み直す。期間外の行がある場合は「対象期間を◯◯まで広げる」（v3.9 の機能を戻す） |
| ⑤誤判定を防ぐ条件 | 空欄を0円としない。円と千円で同じ精度を求めない（千円は丸めの幅を表示し、幅に収まっても「完全一致」とは表示しない）。集計行と内訳行を二重に足さない。税抜経理の税の行、期首・決算振替を区別する。最初と最後の仕訳日が期間内にあるだけで「全件を読み込んだ」と認定しない（月ごとの件数と、帳票との照合で判断する）。月次帳票が自動で表示する当期利益と、締めの仕訳を二重に数えない |
| ⑥必要なCSV列・追加資料 | 基本資料だけ。仕訳：取引日、仕訳番号、借方／貸方の科目・金額・税区分、決算整理仕訳の列（あれば）。帳票：タイトル（事業者名・期間・単位）、科目、期首、各月。追加資料は、差の原因の確認に必要な場合だけ：前期の確定BS、期首残高の明細、CSVの出力条件 |
| ⑦処理を軽くする方法 | 照合は、読込時に作る科目×月の集計（C5）から計算する。データ版が同じなら結果を使い回す。物理行は CSV を読むときに一度だけ記録する |

- **税務・決算への影響**：照合の差は、所得や税額の計算の基礎のずれにつながります。ただし、差だけから「損益の修正が必要」とは決めません。
- **対象者・出典**：法人・個人の両方。複式簿記の原則、S29（純資産のつながり）、監基報520の考え方（S05）。
- **受入条件**
  - 架空データで、期首の欠落、千円の帳票、累計PL、集計行の二重、税抜の税の行、決算整理の各ケースが、正しい状態（一致・差あり・判定保留）と理由になる。
  - 12月決算と3月決算の会社で、対象期間の提案が決算月に合う。
  - セル内改行を含むCSVで、根拠の物理行が元ファイルの行と一致する。

### F02 制度ルール表と適用判定（P0）

**v4.3 との関係**：`B/04:12` の `LAW` と `B/00:3-28` の `SOURCES` を、§1.5.1 の行を持つ表に置き換えます。既存の判定（インボイスの割合、少額減価償却資産、交際費など）は、この表を参照する形に変えます。表の値が同じ間は、結果が変わらないことを確認します。

埋め込みの「消費税区分チェック」（`B/41`）も独自の定数で判定しています。S2 では、少なくとも、そのアプリが使うルール（少額特例・2割特例）について、ルール表と違う点を「制度の確認」の欄に示します。同じ表を使うようにするかは、別のアプリのため、実装時に影響を確かめてから決めます。機能を切ったときのために、既存の `LAW` による判定の経路は残します。

**優先の理由**：期限切れのルール（例：40万円の取得期限がない）や、未成立の改正で断定しないためです。

| 項目 | 内容 |
|---|---|
| ①検出条件 | 候補の判定にルールを使うとき、次の順に調べる。(1) ルールの法的段階が「成立・施行済み」または「成立・将来施行」か（改正案は使わない）。(2) 判定に使う日付の種類（課税仕入れの日、取得日、支出日、貸付年、事業年度の開始日、課税期間、年分など）に対応する値が、CSVか会社設定にあるか。(3) その日付が有効期間に入るか。(4) 対象者（法人／個人、規模、青色など）の条件を満たすか。(5) 境界の日（例：2026/3/31と4/1、2026/9/30と10/1）の前後30日以内か。<br>**判定不能**：必要な日付がCSVになく仕訳日で代えている場合、対象者の設定がない場合、有効期間の外（例：2027/4/1以後に開始する事業年度の交際費800万円特例）。この場合は結論を出さず「確認が必要」とする |
| ②表示する根拠 | 「制度の確認」欄に、使ったルールごとに次を表示する：ルール名、版、法的段階、判定に使った日付の種類と値（「仕訳日で代用」の印つき）、有効期間、対象者、要件、例外、出典（資料名・URL・参照箇所）、確認日。候補の説明には、使ったルールの版を付ける |

| ⑤誤判定を防ぐ条件 | 今日の日付で判定しない。ページの更新日、法令の施行日、会社の適用年度を同じものとして扱わない。法人のルールを個人に使わない（逆も同じ）。設定がなければ両方を候補として示し、結論を出さない。国税庁のタックスアンサーの冒頭注記だけを根拠に、改正のルールを有効にしない。改正前後の両方の期間を含むデータでは、期間ごとに別のルールで判定する |

### F03 月次変動の根拠（P1）

**v4.3 との関係**：前月比・前年同月比、増加先と減少先（相手科目・取引先・品目・部門）、件数、大口、根拠の仕訳は、既にあります（`B/10:187-209,464-489`）。次の点を補います。
- BSの「月末残高の差」と「当月の取引額」を並べて示す
- 返金・取消の明示
- 未選択の額と率
- 前年の条件の確認
- 増加と減少を相殺せずに示すこと

**優先の理由**：利用者が最も多く見る欄で、根拠が欠けると誤解が生じやすいためです。

| 項目 | 内容 |
|---|---|
| ①検出条件 | 比較できる月について、変動の目安（§2.0）を超える科目×月。比較できる条件：両方の月の資料がそろっていること。F01 の照合が「一致」または「差が説明済み」でない科目×月は、比較は表示するが「参考（照合未確定）」の印を付け、原因の説明（原因の候補）は出さない（F04 と同じ扱い）。前年同月は、前期の仕訳帳がその月について完全な場合だけ比べる。<br>**判定不能**：比較する月に未読込がある、前年の範囲が不完全、科目名が変わった（同じ科目か分からない） |
| ②表示する根拠 | (1) 比較金額：当月、前月、前年同月、差額、増減率（前月が0円や負の値のときは率を出さない）。<br>(2) BSでは「月末残高の差」と「当月の借方合計・貸方合計」を別の行に置く。<br>(3) 増加先と減少先は別々の一覧にし、相殺しない。寄与額を符号つきで示し、構成比を無理に100%にしない。<br>(4) 取引先・品目・部門の切り口は別々に見せ、同じ仕訳を複数の切り口で足さない。<br>(5) 未選択の額・件数・率。<br>(6) 大口（上位5件）、返金・取消の候補（同じ相手・同じ額の逆向きの仕訳、マイナスの金額）。<br>(7) 根拠の仕訳一覧：日付、仕訳番号、相手科目、金額、摘要、タグ、元CSVの物理行。50件ずつ表示する |
| ③初心者への説明 | 「広告宣伝費が前月より182,000円増えました。増えた要因は、取引先タグ『A社』の3月8日の仕訳（186,000円）です。ほかの取引先で4,000円減ったため、差し引きで182,000円の増加です。何の広告か、年払いかどうかは摘要だけでは確定できません。請求書の内容と対象期間を確かめてください。」 |
| ④次の行動 | 科目の三角から内訳を開き、寄与の大きい取引を確認する。年払いや一時的な支出なら、その旨を記録する（次回、同じ根拠なら同じ論点として扱う） |
| ⑤誤判定を防ぐ条件 | BSの月末残高と当月の取引額を混ぜない。PLの単月と累計を混ぜない。対象側のタグを使い、空欄を反対側で補わない。仕訳の件数を販売数量と呼ばない。数量・単価がなければ、値上げや販売数量の変化と断定しない。前年と今年の2年分だけで季節性を確定しない。月次償却と決算時の一括償却の違いや、年払いを、異常として扱わない |
| ⑥必要なCSV列・追加資料 | 基本資料。仕訳の取引日・仕訳番号・科目・金額・タグ（借方側・貸方側）・摘要。追加資料は原因の確認に必要な場合だけ（請求書、契約、数量・単価の明細） |
| ⑦処理を軽くする方法 | 共有の索引（C5）から、科目×月×側×タグの集計を引く。上位の集計を先に表示し、根拠の全件は開いたときだけ作る。閉じている欄は描画しない（v4.3 の遅延描画を使う） |

- **税務・決算への影響**：変動の原因によっては、期間帰属、資産計上、交際費、家事関連費の確認につながります（F07・F09・F10 へ渡す）。
- **出典**：S05（分析的手続の考え方）、S06・S08（期間帰属）。
- **受入条件**
  - 架空データで、相殺（増加と減少が両方ある月）、返品・取消、年払い、前月0円、負の値、前年の範囲の不完全の各ケースが、正しい表示と「判定不能」の理由になる。
  - 3つの切り口の合計を足し合わせた数字が、どこにも出ない。

### F04 利益と現預金の差の説明（参考資金増減分析、P1）

**v4.3 との関係**：参考資金増減（`B/11:66-81,187-216`、表示は `B/26`）は、利益、非資金、運転資金、投資、財務、未説明の差に分けています。次の点を補います。
- 区分の細分化
- 法人と個人の区別
- 照合が未確定でも「参考（条件未確定）」として見せること（現状は保留で何も出ない）

**優先の理由**：「利益が出ているのにお金が減った」は、利用者から最も多く出る質問の一つで、BS・PL・仕訳をつなぐ説明の中心だからです。

| 項目 | 内容 |
|---|---|
| ①検出条件 | 月ごとに、現預金の増減（BSの現預金科目の月末差）と、利益（PL単月）の差を分解する。分解する区分は次のとおり。<br>(1) **償却**：減価償却費（非資金）<br>(2) **売掛・在庫・未払**：運転資金。売掛金・未収入金・棚卸資産・前払費用の増減、買掛金・営業上の未払金・前受金の増減<br>(3) **税金**：PLの税金費用と、実際の納付額の差。未払法人税等・未払消費税などの増減<br>(4) **投資**：固定資産の現金での取得・売却（未払での取得は現金の動きに入れない）<br>(5) **借入・返済**：借入の入金と元本の返済。借換は両方を示す<br>(6) **法人の資本取引**：増資・配当など（法人の設定のときだけ）<br>(7) **個人の事業主資金**：事業主貸・事業主借（個人の設定のときだけ）<br>(8) **その他の資産・負債**：仮払消費税・仮受消費税、預り金、貸付金、敷金・保証金、保険積立金など（科目の役割で振り分ける）<br>(9) **未解明差額**：上のどれにも説明できない残り<br>複合仕訳は、仕訳番号で全行をまとめてから分類する。<br>**判定不能**：現預金の範囲（どの口座を含めるか）が未確定、未読込の月、範囲外の口座への振替、外貨 |
| ②表示する根拠 | 月ごとの「つなぎの表」：利益 → 各区分の調整額 → 説明できた現預金増減 → 実際の現預金増減 → 未解明差額。各区分の金額から、根拠の仕訳（仕訳番号・日付・科目・金額）へ移れる。区分ごとに使った科目の一覧と、分類の決め方（例：「未払金のうち、相手科目が固定資産のものは投資へ」）を示す。表の見出しは「参考資金増減分析（正式なキャッシュ・フロー計算書ではありません）」とする |
| ③初心者への説明 | 「3月は利益が100万円出ていますが、現預金は20万円減りました。減った要因は、売上のうちまだ入金されていない60万円（売掛金の増加）、パソコンなどの購入80万円、借入の返済40万円です。増えた要因は、お金の出ていかない費用の減価償却20万円と、まだ支払っていない費用の増加37万円です。説明できない差が3万円残っています。」（個人の場合）「事業主貸の50万円は、事業のお金を事業主が引き出した額で、経費ではありません。」 |
| ④次の行動 | 未解明差額が大きい月だけ、根拠の仕訳を開く。分類が分からない複合仕訳は、明細（返済予定表、通帳）を確認する。期限が分からない債権債務を、予定の表には入れない |
| ⑤誤判定を防ぐ条件 | 複合仕訳で、行の順番から相手科目を決めない。口座間の振替は除き、振込手数料は残す。貸倒れによる売掛金の減少を入金にしない。未払での設備購入を、営業の買掛金の増加に混ぜない。リース・現物出資・外貨の換算を現金の動きにしない。税引前利益から始める場合と税引後利益から始める場合で、税金を二重に引かない。カード利用時の費用と、口座引落による現金の減少を二重に数えない。未解明差額を強制的に0にしない |
| ⑥必要なCSV列・追加資料 | 基本資料。現預金の範囲（科目の役割の設定。v4.3 の `accountRoles` を使う）、期首・前月末の現預金。追加資料は分類できない場合だけ（返済予定表、通帳、固定資産の購入資料） |
| ⑦処理を軽くする方法 | 仕訳番号→全行の索引と、現預金の行の索引（C5）を使う。根拠は参照（仕訳番号）だけを持ち、画面ごとに仕訳の全件を複製しない |

- **税務・決算への影響**：資金の動きそのものは課税の結論ではありません。ただし、税金の納付の時期（S22）、借入と経費の混同、事業主貸に入れるべき私的支出の確認につながります。
- **対象者・出典**：法人・個人の両方。区分（6）と（7）は会社の設定で切り替えます。S30（資金の範囲と区分）、S43（税金の表示）、S22。
- **受入条件**
  - 架空データで、次の各ケースの区分と未解明差額が正しくなる：貸倒れ（非資金）、口座間振替と手数料、借換、未払での設備購入、事業主貸借、税金の未払と納付、カードの利用と引落。
  - 照合が未確定のときも「参考（条件未確定）」として表示され、確定とは書かれない。

### F05 債権債務の動きと残高の確認（P1）

**v4.3 との関係**：取引先別の候補と残高（`B/12`）、集中度（`B/13`）、期首の範囲つき推計（`B/15`）、期日一覧があるときの延滞判定は、既にあります。v3.9 にあった次の機能は、原則（推測で確定しない）に合わせて戻します。
- 過去の仕訳からの期首推定
- 回収・支払の停滞判定

**優先の理由**：回収できていない取引先は、資金と税務（貸倒れ）の両方に影響するためです。

| 項目 | 内容 |
|---|---|
| ①検出条件 | (1) **記録上の事実**：取引先別に、当月の増加（売上・仕入の計上）と減少（入金・支払・相殺・返品）。対象科目の側のタグを使う。<br>(2) **確定残高**：BS×取引先の帳票があれば、その月末残高（帳票の値）。<br>(3) **継続残高の候補**：確定残高があり、0円でない残高が3か月以上（目安）減っていない取引先。<br>(4) **参考推計**：確定残高がない場合だけ、過去の仕訳から期首を推計する（v3.9 の方法）。結果は「参考推計（確定ではありません）」と明示し、初期状態は閉じて表示する。**推計値は (3) 継続残高の候補、F04、F11、F12、合計のどれにも使わない**（期首の内訳を推計で作らないため）。<br>(4b) **カード（未払金）**：「利用先別の当月の増減」（利用側の仕訳のタグ）と「月末の未払残高」を別の表にする。引落側のタグが空なら、月末の未払の利用先別の内訳は「不明」とし、利用側の比率で配分しない。<br>(5) **減少の種類**：減少の相手科目で、入金（現預金）、相殺（買掛金など）、返品・値引（売上のマイナス）、貸倒れ（貸倒損失）、振替（他の債権科目）に分ける。<br>(6) **取引先が未選択の入金・支払**：額・件数を残す。<br>**判定不能**：請求日、支払期限、請求番号、消込の対応がない場合、「期限を過ぎた」「何か月未回収」「消込済み」は判定しない |
| ②表示する根拠 | 取引先ごとに、期首（帳票の値／参考推計／不明）、当期の増加と減少、月末残高、残高の根拠（帳票の行、または推計の方法）。減少の種類ごとの内訳と根拠の仕訳。未選択の入金・支払の一覧。参考推計には、使った期間・方法・確からしさを付ける |
| ③初心者への説明 | 「B社の売掛金は、6月から残高が220,000円のまま減っていません。支払期限の情報がないため、延滞かどうかは分かりません。請求書と入金の明細で、回収の予定を確かめてください。」／「C社の売掛金が減った理由は、入金ではなく、買掛金との相殺（4月15日の仕訳）です。」 |
| ④次の行動 | 継続残高の候補について、請求先別の明細と入金の消込を確認する。回収の見込みに不安があれば、契約・担保・取引の状況を確認する。期首の取引先別内訳が必要な場合だけ、期首の債権債務の明細を求める |
| ⑤誤判定を防ぐ条件 | 期首の取引先別内訳を、科目合計から配分して作らない。先入先出・同額・同じ名前・残高が動かないことは、確認の候補にとどめ、消込の事実にしない。長く残っているだけで貸倒れの候補にしない（法人の「取引停止後1年」の扱いは売掛債権に限り、取引停止の日が必要）。BSの取引先別の値で、未選択に相殺額がある科目（現預金・カードなど）は、残高ではなく累計の動きとして扱う（v3.9 で確認した freee の性質）。回転期間は、平均残高と分母がそろう場合の補助指標にとどめ、期限超過の証明には使わない |
| ⑥必要なCSV列・追加資料 | 基本資料。BS×取引先（あれば）。仕訳の借方・貸方の取引先。本当の滞留・期限の分析には、期首の債権債務の明細、請求番号と決済の対応、支払期限が必要。これらは候補の確認で必要になった場合だけ求める |
| ⑦処理を軽くする方法 | 取引先×科目×月の索引（C5）から候補だけを抽出する。取引の総当たりの照合はしない。参考推計は、開いたときだけ計算する |

- **税務・決算への影響**：貸倒れ（法人：S14、個人：S15）、費用・収益の帰属（S06、S07、S41）の確認につながります。
- **受入条件**
  - 架空データの継続残高（v3.9 のテストにある取引先）が候補として出る。
  - 「延滞」「期限超過」の語が、期日の資料がないときに出ない。
  - 減少が相殺・返品・貸倒れの仕訳のとき、入金と表示されない。
  - 実データのBS×取引先で、現預金・カードの取引先別の値が残高として表示されない。

### F06 仮勘定・立替の解消確認（P1）

**v4.3 との関係**：仮勘定の検出は、月末残高一覧を読んだときだけです（`B/00:257-263`）。月次BS・タグ別BS・仕訳から検出する機能を新しく作ります（v3.9 の tag-clearing を発展させる）。

**優先の理由**：仮払金・立替金などの残り方は、精算漏れ、私的な支出、役員への貸付などの重要な論点の入口だからです。

| 項目 | 内容 |
|---|---|
| ①検出条件 | 対象科目：仮払金、仮受金、立替金、立替経費、前渡金・前受金（科目の役割の設定で追加できる）。<br>(1) 科目の残高が0円でなく、3か月以上（目安）動いていない。<br>(2) 増加（発生）の仕訳に対応する減少（解消）の仕訳がない状態が続いている。同じ摘要・取引先の増加が繰り返し起きている。<br>(3) タグ別BSで、タグごとの残高が動かずに残っている。科目合計が0円でも、タグごとに±の残高が残る場合を含む（タグの付け違いの可能性）。<br>(4) 正当な理由が記録された論点（例：長期の預託）は、根拠の指紋（C2）が変わるまで再警告しない。ただし、事業年度の末日を過ぎたとき、または動いていない月数が記録時から3か月を超えて増えたときは、記録を残したまま再び候補にする。抑えている間も、F11 の決算までの確認一覧には「理由を記録済み」として表示する。<br>**判定不能**：期首の残高があり、その発生時期が分からない場合（当期に最初に観察した日を発生日としない） |
| ②表示する根拠 | 科目・タグごとに、観察できる期間、期首（または最初に観察した月）、増加と減少の各仕訳（日付・仕訳番号・相手科目・金額・摘要）、残高の推移、動いていない月数。タグ別BSの場合は「科目合計 0円／タグ別：A +230,000円、未選択 −230,000円」のように示す |
| ③初心者への説明 | 「立替金のうち、品目『登録手数料』の残高が4か月同じ額のまま残っています。科目全体では0円ですが、品目ごとに見るとプラスとマイナスが残っています。精算の仕訳に品目を付け忘れた可能性と、精算そのものが終わっていない可能性があります。」 |
| ④次の行動 | 精算書・入出金の目的・立替の相手を確認し、処理（費用、前払、貸付など）を決める。正当な理由があれば記録する（同じ根拠のまま再び警告しない） |
| ⑤誤判定を防ぐ条件 | 科目名だけで、費用・売上・貸付に振り替えない。最初に観察した日を発生日としない。科目合計が0円でも、タグの付け違いと精算漏れのどちらかは確定しない。法人の役員への立替は、経済的利益の論点（S19）として F09 に渡すが、給与課税を確定しない |
| ⑥必要なCSV列・追加資料 | 基本資料。月次BS（科目合計）、タグ別BS（あれば）、仕訳の摘要・タグ。追加資料は対象の論点だけ（精算書、契約、立替の相手の確認） |
| ⑦処理を軽くする方法 | 対象科目に限った増減の索引を作る。対応済みの論点は、根拠の指紋で変化を調べるだけにする |

- **税務・決算への影響**：実態によって、費用、前払費用、貸付金、給与等の可能性があります。法人は役員への経済的利益（S19）が論点になります。
- **受入条件**
  - 架空データの立替金（タグ別で±が残り、科目合計は0円）が候補として出る。
  - 正当な理由を記録した論点は、同じ根拠のままなら再び出ず、根拠が変わると再び出る。

### F07 継続費用と期間帰属（P2）

- **受入条件**：架空データで、計上漏れの月、二重の月、年払い、科目の変更が、比較する過去の取引つきで出る。

### F08 粗利と取引構成（P2）

**v4.3 との関係**：売上の集中度（`B/13`）とタグ別の内訳は既にあります。v3.9 のタグ別分析（構成、集中度、新規・離脱、部門別損益）を v4.3 の帳票の形（`reportViewDimension`）に合わせて移し、粗利率の推移を加えます。

| 項目 | 内容 |
|---|---|
| ①検出条件 | (1) 粗利率（売上総利益÷売上）の比較できる月の変化。(2) 取引先・品目・部門ごとの構成比と増減の寄与。(3) 上位の取引先への集中（上位1・3社の比率）、新しい取引先・いなくなった取引先。(4) 部門別損益（PL×部門があるとき）。(5) 未選択の比率。<br>**判定不能**：月次の在庫・原価が確定していない（棚卸資産が期中に動かない）場合は、粗利を「暫定」とする。売上が0円の月、返品で負の値の月は率を出さない |
| ②表示する根拠 | 算式、使った原価科目、在庫の処理の有無、タグの未選択率、上位の内訳と根拠の仕訳 |
| ③初心者への説明 | 「3月の粗利率は前月より8ポイント下がりました。月次の棚卸をしていないため、この粗利は暫定です。原価の増加、商品の構成の変化、在庫の処理が関係する可能性があります。」 |
| ④次の行動 | 月次の棚卸・原価処理の有無を確認する。精度が必要な場合だけ、数量・単価・商品の明細を求める |
| ⑤誤判定を防ぐ条件 | 仕入額をそのまま原価としない。タグの意味（請求先・入金名義・紹介者のどれか）を確認するまで「主要顧客」と断定しない。品目タグから数量・単価・税率を推定しない。業種別の統計を誤りの基準にしない |
| ⑥必要なCSV列・追加資料 | 基本資料。PL×取引先・品目・部門（あれば）。追加資料は精度が必要な場合だけ |
| ⑦処理を軽くする方法 | 月次の集計（C5）を使い、切り口ごとに全仕訳を読み直さない |

- **税務・決算への影響**：期末在庫の計上漏れや原価の期間のずれは、利益と所得を変えます（法人：S33・S34、個人も同様の考え方）。構成や集中度そのものは税務の結論ではありません。
- **対象者・出典**：法人・個人の両方。S33、S34。業種別の統計（S32）は比較の参考にとどめます。
- **受入条件**：架空データで、粗利の暫定表示、集中度、部門別損益、未選択の比率が出て、3つの切り口を足し合わせた数字が出ない。

### F09 法人／個人の資金と税務の確認（P2）

**v4.3 との関係**：役員報酬、損金不算入の税、受取利息（法人）、私的支出と預金利息（個人）、役員との貸借（チェックシート）は既にあります。法人と個人の切替を会社設定に揃え、貸付の利率と事業主資金の説明を補います。

| 項目 | 内容 |
|---|---|
| ①検出条件 | **法人**：<br>(1) 役員貸付金・役員借入金の増減と受取利息の有無。<br>(2) 役員報酬の月額の変化（会計期間の開始から3か月を過ぎた変化）。<br>(3) 役員への立替・仮払の残高（F06 から）。<br>(4) 交際費の飲食費の候補（支出日、1件あたりの金額）。<br>**個人**：<br>(1) 事業主貸・事業主借の動き（生活費・税金・保険などの摘要の候補）。<br>(2) 家事関連費の候補科目（地代家賃、水道光熱費、通信費、車両費など）で、事業主貸への振替がないもの。<br>(3) 家族への支払の候補（会社設定で専従者ありのときだけ）。<br>(4) 預金利息の扱い。<br>**判定不能**：法人／個人が未設定、関連当事者の情報がない、貸付日がない |
| ②表示する根拠 | 記録上の事実（科目・日付・金額・相手・摘要）と、判断に足りない条件（貸付日、利率、議事録、使用割合の根拠、生計を一にしているか、年齢、届出）を並べる。使ったルール（PIT-LOAN-RATE など）の版と出典 |
| ③初心者への説明 | 「役員貸付金が2026年4月に300万円増え、受取利息の計上がありません。貸付けた年が2026年なら、利息の基準は年1.3%です。ただし、合理的な利率を定めた場合や、利息の差額が年5,000円以下の場合などの例外があります。契約書と貸付日を確認してください。」（個人）「租税公課に、所得税の納付と思われる支出があります。所得税は必要経費にならないため、事業主貸への振替を確認してください。」／「事業主貸が前月末より増えています。記録上の相手（取引先タグ）は『B』です。生活費・立替・貸付など、何の資金移動かは摘要だけでは確定できません。通帳や明細を確認してください。」（タグの名前を実際の受取人とは断定しない。現預金との対応を仕訳全体で確認できた場合だけ「帳簿上の支払」と書く） |
| ④次の行動 | 用途・関連当事者・契約・配分の根拠・給与や専従者の条件を確認する。一度確認した会社の情報（専従者の有無など）は使い回す |
| ⑤誤判定を防ぐ条件 | 科目・摘要・取引先名だけで、私用・役員・親族・税率を断定しない。法人のルールを個人に使わない（逆も同じ）。貸付の残高だけで給与課税を確定しない。家事按分の比率を科目名から作らない |
| ⑥必要なCSV列・追加資料 | 基本資料と会社設定（法人／個人、決算月、専従者の有無）。追加資料は対象の論点だけ（契約書、議事録、使用割合の根拠、届出書） |
| ⑦処理を軽くする方法 | 条件に合う科目だけを読む。個人情報を外部に送る処理は作らない |

- **税務・決算への影響**：法人では、役員への貸付の利息が基準より低い場合や、会社が役員の私的な支出を負担した場合に、経済的利益として役員の給与になり、源泉徴収や損金不算入につながることがあります（S18、S19、S20）。法人税・住民税の本税などは損金になりません（S22）。個人では、家事上の経費や所得税・住民税は必要経費になりません（S08）。事業主貸・事業主借の動きそのものは、所得の計算に入りません。どの場合も、CSVだけでは結論を出しません。
- **対象者・出典**
  - 法人：S18（役員給与）、S19（経済的利益）、S20（貸付の利率）、S42（交際費）、S22（租税公課）
  - 個人：S08（家事関連費・家族）、S37（専従者）、S21（利子）
- **受入条件**：法人と個人の設定を切り替えると、出る候補と根拠が入れ替わる。設定がないときは両方が「候補」として出て、結論がない。

### F10 固定資産と償却（P2）

**v4.3 との関係**：高額な消耗品・修繕、同じ相手の合算、物品の費用計上は既にあります（`B/04:152-165,204,210`）。次の点を補います。
- 取得と償却の対応
- 除却・売却の候補
- 少額特例の期限と年間の合計（F02 のルール表を使う）
- 誤判定を防ぐ条件（法基通7-5-1(6)）

| 項目 | 内容 |
|---|---|
| ①検出条件 | (1) 資産科目への取得の仕訳と、費用科目の高額な物品の支出（目安：10万円以上）。<br>(2) 少額特例の境界：仕訳日で代用した取得日について、2026/3/31以前なら30万円、2026/4/1以後なら40万円の前後の金額。2029/3/31より後は特例を適用しない。<br>(3) 特例の候補の年間合計（年300万円の目安。法人の短い事業年度、個人の開業・廃業の年は月数で按分）。<br>(4) 資産の残高があるのに償却の仕訳が一度もない（決算月だけの償却は正常として扱う）。<br>(5) 資産科目の減少と、売却・除却の科目の動き。<br>(6) 修繕費の形式基準の前後（20万円未満、またはおおむね3年以内の周期。60万円未満、または取得価額のおおむね10%以下）。<br>**判定不能**：資産単位、取得日・供用開始日、青色申告か、規模の要件が分からない |
| ②表示する根拠 | 仕訳（日付・科目・金額・取引先・摘要）、使ったルールの版と境界、「仕訳日で代用」の印、特例の候補の合計と内訳 |
| ③初心者への説明 | 「2026年5月に消耗品費で35万円のパソコンが計上されています。少額減価償却資産の特例では、2026年4月1日以後の取得は40万円未満が対象です。ただし、青色申告であること、資産の単位、使い始めた日、年300万円の上限などの要件があります。」 |
| ④次の行動 | 固定資産台帳、請求書、資産の単位、取得日・供用開始日、用途を確認する。修繕は工事の内容を確認する |
| ⑤誤判定を防ぐ条件 | 金額だけで即時の経費にしない。仕訳日を取得日・供用開始日の代わりに確定値としない。月次に償却がないだけで漏れとしない。おおむね60万円以下の少額資産を消耗品費で損金経理した額は、償却費として扱われる（法人、S11）ため、「償却の漏れ」と判定しない。修繕費か資本的支出かを金額だけで決めない |
| ⑥必要なCSV列・追加資料 | 基本資料。追加資料は対象の候補だけ（固定資産台帳、請求書、取得・供用の資料） |
| ⑦処理を軽くする方法 | 資産科目×月の索引で照合する。台帳がなければ候補の一覧にとどめる |

- **税務・決算への影響**：法人では、償却費は損金経理した額のうち償却限度額までが損金になります（法人税法31条。損金経理の範囲は S11）。少額減価償却資産の特例は、損金経理と別表16(7)の添付が要件です（S09）。個人は、所得税の計算方法で求めた償却費を必要経費にします（S10）。資産を費用にした額、特例の年300万円を超えた分、修繕費と資本的支出の区分（S12、S13）は、所得の差になります。
- **出典**：S09〜S13。法人は措法67の5、個人は措法28の2。
- **受入条件**：2026/3/31と4/1、2029/3/31と4/1の境界で、金額の基準と「特例なし」の切替が正しい。消耗品費の60万円以下の資産が「償却の漏れ」として出ない。

### F11 決算までの確認一覧（P2）

**v4.3 との関係**：対応ワークフローの区分・最終確認・追加資料の依頼の下書き・チェックシートは既にあります。会社の条件（法人／個人、決算月、消費税の方式）ごとの決算チェックを、自動でまとめる部分を補います。

| 項目 | 内容 |
|---|---|
| ①検出条件 | 会社の条件から、決算までに確認する項目を作る：棚卸、償却、未払・前払、税金（法人税等、事業税、消費税、防衛特別法人税）、給与・源泉、届出の期限、交際費。そこに、F01〜F10 で未完了の候補をつなぐ。<br>主な項目の条件：<br>・防衛特別法人税：2026/4/1以後に開始する事業年度の法人。税額が0でも申告が必要。<br>・簡易課税制度選択届出書の提出期限の特例：2割・3割特例を使った課税期間の翌課税期間。<br>・交際費800万円の特例：2027/3/31までに開始する事業年度。<br>・少額特例の年間合計。<br>**判定不能**：会社の条件が未設定（その項目は「設定が必要」として出す） |
| ②表示する根拠 | 項目ごとに、根拠のルール（版・出典）、つながっている候補、証拠の4段階（C3）の状態 |
| ③初心者への説明 | 「決算までに確認することが12件あります。そのうち5件は、まだ資料の確認が終わっていません。」 |
| ④次の行動 | 未確認の項目だけを順に確認する。確認の根拠（証憑、申告・届出）を記録する |
| ⑤誤判定を防ぐ条件 | 「修正済み」は利用者の対応状態であり、freee の元帳を直したことの証明ではない。再取込で該当の変更を照合できた場合だけ「帳簿の変更も確認」と別に表示する。証憑・届出・税務の要件の確認は、根拠を記録した場合だけ「確認済み」にする。本アプリのバックアップを、帳簿書類の法定保存の代わりにしない（S35、S40） |
| ⑥必要なCSV列・追加資料 | 基本資料と会社設定。追加資料は該当の項目だけ |
| ⑦処理を軽くする方法 | 候補IDと状態の差分だけを集計する。全体の作り直しは、データ版が変わったときだけ |

- **税務・決算への影響**：決算の手続きと、申告・届出の期限の確認漏れを防ぎます。各項目の税務の結論は、それぞれの機能とルール表（F02）に従い、この一覧では出しません。
- **対象者・出典**：法人と個人で項目を分けます。防衛特別法人税（S45）、簡易課税の届出期限の特例（S25）、交際費（S42）、少額減価償却資産（S09、S10）など、§1.5.1 の各行のとおりです。
- **受入条件**：法人（3月決算）、法人（12月決算）、個人で、出る項目が正しく入れ替わる。2026/4/1の前後に開始する事業年度で、防衛特別法人税の項目の有無が切り替わる。

## 3. 段階的な実装案（既存機能を保つ）

### 3.1 方針

1. **v4.3 を土台にします。** 取込、列対応、集計、会社ID、保存データ、確認キュー、対応ワークフロー、メモ、履歴、バックアップの仕組みは作り直しません。新しい分析は、既存の関数を包む小さなモジュールとして足します。v4.3 自身も、この方法で ReviewReportViews や ReviewResponseWorkflow を追加しています。
2. **新しい保存データは、1つの名前空間にまとめます**（`session.v44`）。既存のキーの意味は変えません。新しいキーは必ず `validateSession` に登録します（§1.4）。
3. **機能ごとに切り替えられるようにします。** 切るとv4.3と同じ動作に戻り、既存のデータ・状態・バックアップがそのまま使える状態を保ちます。
4. **判定する関数には副作用を持たせません。** 判定は事実を受け取り、候補・不足資料・根拠を返すだけにします。保存・画面の更新は別の層で行います。
5. **通信を追加しません。** 有料API、外部AIへの顧客CSVの送信、freee との同期・書戻しは作りません。
6. **Worker 用の文字列（`B/36`）は、ビルドで作ります**（R8 の対策）。手作業の同期をやめます。

### 3.2 ファイルの構成（作業の土台）

Claude版v3.9 のリポジトリと同じ方式を使います。土台のHTMLは変更せず、`src/` の差分を組み込んで配布ファイルを作ります。

| `build.py` | 土台に `src/` を組み込み、`dist/自計化レビュー_v4.4.html` を作る。`--check` で、変更していないブロックが土台と同じかを確認する。**Worker 用の文字列を、エンジン系のブロックから作り直す** |
| `tests/` | 架空データと、Node・ブラウザのテスト |

### 3.4 新しい保存データ（`session.v44`）

```js

  links: { [issueKey]: { findingIds: [/* 過去に付いた候補ID（最新が最後） */],
```

- **登録**：`E.newSession` と `E.validateSession` をラッパーで包み、`session.v44` の形と上限（件数・文字数）を検証して写します。
  - v4.3 の ReviewResponseWorkflow（`B/19:53-55`）と同じ方法です。
  - Worker 用の文字列にも同じモジュールを入れます（ビルドで自動）。
- **上限**：`links` と `evidence` は5,000論点まで、メモは各4,000字まで。対応ワークフローの上限に揃えます。

### 3.5 論点キーと指紋の作り方（F00 の要）

- **論点キー**：v4.3 の `anchor()`（`B/19:98`：候補の種類と文脈、または種類＋科目＋月）を土台に、次を足して、正規化（NFKC・空白除去）した文字列にします。
  - 新しい機能の候補ではルールID、既存の候補では理由の種類（タイトルの雛形の番号。金額などの値は除く）
  - 切り口とタグ
  - 取引単位の候補では、仕訳番号の集合（並べ替えたもの）
  - **入れないもの**：理由文の本文、金額、重要性、`financial` の設定、ファイル名、取込の識別子、行番号
  - キーを作れない候補（科目も月もない、全体の注記など）には付けず、従来どおり候補IDだけで扱います。
- **同じキーが複数あるとき**：今回の候補が2件以上、または過去の記録が2件以上、同じ論点キーを持つ場合は、自動で引き継ぎません。「手で対応づけが必要」と表示し、利用者が選んだ記録だけを引き継ぎます。
- **根拠の指紋**：仕訳は「仕訳番号＋日付＋科目＋側＋金額＋税区分＋対象側のタグ」、帳票は「種類＋科目＋月＋切り口＋タグ＋金額」を並べてハッシュします。取込の指紋・行番号・ファイル名・設定は入れません。
- **前提の指紋**：使ったルールのIDと版、関係する会社の事実、候補を絞る目安の値を並べてハッシュします。
- **衝突への備え**：論点キーはハッシュにせず文字列のまま保存します。指紋は v4.3 と同じ32ビットのハッシュですが、同じ論点キーの中だけで比べるため、別の論点と取り違えることはありません。

### 3.6 引継ぎと無効化の手順（F00）

**既存の構造に書く値の約束**：`responseWorkflow`・`decisions`・`manual` には、v4.3 の検証を通る値だけを書きます。新しい事象の種類を足したり、記録のキーを付け替えたりしません。引継ぎの詳細は `session.v44` にだけ持ちます。

1. **分析のあと**（`E.analyze` のラッパー）：各候補に論点キー、根拠の指紋、前提の指紋を付けます。
2. **引継ぎ**（`ReviewResponseWorkflow.build` の前）：今回の候補の論点キーに、`v44.links` の記録がある場合
   - **根拠と前提の指紋が両方とも同じ**、かつ同じキーの候補・記録が1件ずつのとき：今回の候補IDに、前回の記録の内容を写した**通常の対応記録**を作ります。
     - 履歴の事象は既存の `saved` を使い、要約に「前回の記録から引継ぎ」と書きます。
     - `findingSnapshot` は今回の候補で作ります（`id` をキーと一致させる）。
     - 完了の条件（`completionChecks`）を満たす場合だけ完了にし、満たさなければ再検証にします。
     - 前回の候補IDの記録はそのまま残します。
   - **どちらかの指紋が違う**とき：前回の判断と、確認の4区分の記録を `v44.snapshots` に写し、今回の候補の記録を再検証として作ります。変わった根拠の行と、変わった前提を表示します。
3. **完了の失効の判定**（`build` のラッパー）：v4.3 は、会社全体のトークンが変わると完了を再検証として表示します（`B/19:121-123`）。v4.4 では、論点ごとに根拠と前提の指紋、および `taskImportToken`（`B/19:84`）が変わっていなければ、完了のまま表示します。保存データの値は変えず、表示の判定だけを変えます。
4. **呼び出し元ごとの無効化**（`invalidateChecks` の11か所と、網羅性の確認のOFF）

| 呼び出し元 | 操作 | v4.4 の扱い |
|---|---|---|
| `B/43:217` | 対象期間などの条件の変更 | 全件を再確認（従来どおり）。理由を記録する |
| `B/43:436` | 会社区分（法人／個人）の変更 | 全件を再確認（従来どおり） |
| `B/43:359` | 資料の取込 | 取り込んだ種類の指紋が同じなら何もしない（網羅性の確認・照合条件の確認も戻さない）。違えば、その種類を根拠に含む論点だけを再確認にし、当期の仕訳帳なら網羅性の確認をOFFにする |
| `B/43:397` | 資料の削除 | その種類を根拠に含む論点だけを再確認にする。当期の仕訳帳なら網羅性の確認をOFFにする |
| `B/43:402` | 科目の役割の変更 | その科目を根拠に含む論点だけ |
| `B/43:405` | 照合条件・期日一覧の設定 | 前提の指紋で判断する（ONにしただけで、根拠の同じ完了を戻さない） |
| `B/43:411` | 網羅性の確認 | 同上 |
| `B/43:422` | 過去仕訳の決算整理の扱い | 過去の仕訳帳を根拠に含む論点だけ |
| `B/43:423` | 過去資料の確認状態 | その過去資料を根拠に含む論点だけ |
| `B/43:439` | 重要性の設定 | 前提の指紋で判断する（目安の値が前提に入るため、関係する論点だけが再確認） |
| `B/43:440` | 残高の手入力 | 残高一覧を根拠に含む論点だけ |

   - チェックシートの項目は、項目ごとに関係する資料の種類を表で持ち、その種類が変わったときだけ戻します。
5. **復元の重複**（`W.merge`）：S0 で、復元した会社を開き直したときに変わる項目を実測し、その項目だけを除いて比べます（`updatedAt`・`summary` などを想定）。同じ会社IDで内容が違う場合は、黙って飛ばさず、「置き換える／別の会社として追加する／とばす」を選んでもらいます。
6. **切替**：「従来どおり、資料を読むたびに全件を再確認に戻す」の切替を設定に置きます（初期値はオフ）。

```js
  periods: [ { from: '2006-04-01', to: '2026-03-31', value: { limitYen: 300000 } },
             { from: '2026-04-01', to: '2029-03-31', value: { limitYen: 400000 } } ],
  appliesTo: { entity: ['corp', 'individual'],
               corp: ['青色申告の中小企業者等', '常時使用する従業員400人以下（特定法人300人以下）'],
               individual: ['一定の青色申告者'] },
```

- **判定の関数**：`resolve(ruleId, { date, dateKind, entity, facts })` が `{ status, value, rule, proxy, missing }` を返します。

### 3.9 処理を軽くする方法

- **索引は一度だけ**：分析（`analyze`）の中で作り、会社・データ版・設定・ルールの版が同じなら使い回します。科目数や取引先数に比例して、全仕訳を読み直しません。
- **Worker と画面の分担**：Worker は分析と読込の正規化だけを行い、結果は複製として画面に戻ります（`B/21:54-58`）。そのため、画面の描画（`F.page`）は索引を直接使えません。判定に必要な集計は分析の結果に含めて返し、根拠の一覧は件数を絞った参照（仕訳番号など）として返します。全件の根拠は、画面側で開いたときに作ります。
- **ハッシュの材料を減らす**：論点キーは識別に必要な項目だけにします。v4.3 の候補IDの計算（`B/00:165,205-211`）は、互換のため残します。ただし、全項目の文字列化を減らせるかは、S6 で計測してから判断します（IDが変わるため、F00 の引継ぎが入ってからにする）。
- **描画を減らす**：上位の集計と根拠50件を先に表示し、続きはページ送りにします。閉じている欄は描画しません（v4.3 の方式を使う）。
- **メモや状態の変更では再集計しない**（v4.3 の方式を保つ）。
- **計測**：§4.5 の規模で、時間・メモリ・保存データの大きさを測ります。秒数の目標を検証なしに約束しません。

### 3.10 戻し方

- **機能ごとの切替**：`workspace.preferences.v44Features` に機能ごとのオン／オフを持ちます。v4.3 の `W.validate` は `preferences` の `theme` しか残さない（`B/38:25`）ため、`W.validate` も包んで登録します。オフにした機能は分析も表示もせず、v4.3 と同じ結果になります。F02 をオフにしたときのために、既存の `LAW` による判定の経路は残します。
- **保存データ**：新しい情報は `session.v44` にだけあります。既存の構造には v4.3 の検証を通る値だけを書くため（§3.6）、v4.3 で v4.4 のデータを開くと、`session.v44` と `preferences.v44Features` だけが捨てられ、既存の記録・資料は残ります。これは S1 の受入確認で、IndexedDB とバックアップの両方について実際に確かめます（確かめるまでは「想定」です）。
- **アップグレードの前に**：v4.4 を最初に開いたとき、全社バックアップを書き出すよう案内します。旧版のファイルは、利用者の手元にそのまま残します。
- **ビルドの戻し**：`build.py` は段階ごとに新しいモジュールを登録する表を持ちます。表から外せば、その段階を除いた配布ファイルを作れます。

| 会社ID・会社切替 | IDが変わらない。切替で資料・記録が残る |
| 確認キュー・状態・修正済み・メモ | 3系統の状態の値と保存先が変わらない |
| 履歴 | 対応記録の履歴（最大40件）が消えない。引継ぎ・再確認の事象が追加される |

### 4.5 性能の確認

| 規模（架空） | 測るもの | 判断の基準 |
|---|---|---|
| 等倍（仕訳 約300行、帳票 8本） | 読込、分析、月次画面の表示、DOM の数、保存データの大きさ | v4.3 の基準と比べる |
| 25倍（仕訳 約7,250行） | 同上。v4.3 の実測：読込18.4秒、再チェック6.1秒、保存データ15.6MB | 既存の処理が、v4.3 の基準より遅くならない。新しい分析を足した時間を記録する |
| 100倍（仕訳 約29,000行） | 同上と、メモリの最大値 | 画面が固まらない（Worker で処理）。異常に大きくならない |
