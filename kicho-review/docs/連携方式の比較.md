# freee との連携方式の比較（2026-11-11 調査）

記帳レビューが freee のデータを受け取る方法を、公式資料で確認できた範囲で比べます。**確認できなかったことは「未確認」と書き、推測で埋めていません。**

## 確認した資料

| 資料 | 確認できたこと |
|---|---|
| freee 会計 API の公開スキーマ（[freee/freee-api-schema](https://github.com/freee/freee-api-schema) `v2020_06_15/open-api-3/api-schema.json`） | 下の「API で取得できるデータ」の全項目、1日あたりの回数上限 |
| [アクセストークンを取得する](https://developer.freee.co.jp/startguide/getting-access-token)、[トークンの有効期限](https://developer.freee.co.jp/reference/faq/token_lifetime)、[アクセス権限](https://developer.freee.co.jp/reference/access-token-permission) | OAuth の方式、有効期限、権限の考え方 |
| freee ヘルプセンター（仕訳帳CSVの仕様など） | **自動取得が拒否され（403）、今回は読めていません** |

## API で取得できるデータ（スキーマで確認）

| 用途 | エンドポイント | レビューで使える内容 |
|---|---|---|
| 仕訳帳 | `GET /api/1/journals`（作成依頼）→ `…/reports/{id}/status` → `…/download` | 非同期でファイルを作る。形式は `generic`（旧CSV）・`generic_v2`（新CSV）・`csv`（弥生）・`pdf`。文字コードは未指定だと Shift_JIS。**`generic` のみ `visible_ids[]` で取引ID・振替ID・振替伝票IDを列に追加できる** |
| 取引 | `GET /api/1/deals` | 発生日・金額・取引先・明細行・決済状況・**`deal_origin_name`（登録元の表示名。例：手動、自動で経理、経費精算）**・添付証憑 |
| 口座明細 | `GET /api/1/wallet_txns` | 日付・金額・入出金・残高・摘要・**`status`（消込待ち／消込済み／無視）**・**`rule_matched`（自動登録ルールに当たったか）** |
| 自動登録ルール | `GET /api/1/user_matchers` | 条件・科目・税区分・適用件数・最終更新者 |
| 振替伝票・口座振替 | `GET /api/1/manual_journals`、`/api/1/transfers` | 決算整理フラグ、口座間の振替 |
| マスタ | `/api/1/partners`、`/account_items`、`/taxes/companies/{id}`、`/walletables`、`/companies` | 取引先、科目（区分つき）、税区分、口座、事業所 |
| 試算表 | `/api/1/reports/trial_bs`、`trial_pl` ほか | 残高・月次推移 |

- 認可：OAuth 2.0 の認可コード方式。トークンの取得例に `client_secret` が含まれる。アクセストークンは6時間。リフレッシュトークンは90日（別のページには「期限なし→90日に変更予定」とあり、記述が食い違う）で、1回使うと使えなくなる。
- 権限：アプリに設定した権限と、freee 側でそのユーザーに設定された権限の両方で決まる。スコープは `read`／`write`。
- 回数上限：事業所×アプリごとに1日 3,000回（法人アドバンスは 5,000、エンタープライズは 10,000）。
- 契約プランによって使えるAPIが異なる（例：総勘定元帳APIは上位プランのみ）。

**未確認**：ブラウザのJavaScriptから直接呼べるか（CORS）／会計事務所（アドバイザー）のアカウントで顧問先の事業所をAPIから読むときの条件／各顧問先のプランで必要なAPIが使えるか／取引・仕訳の画面を直接開くURLの形式（スキーマにも開発者サイトにも記載なし）。

## 方式の比較

| | A. CSV取込（現在） | B. freee API（読み取り専用） | C. ブラウザ拡張 |
|---|---|---|---|
| 取得できるデータ | 仕訳帳の列だけ。取引ID・登録経路・口座明細の状態はない | 取引ID、**登録元**、**自動登録ルールの適用**、口座明細（未処理・無視を含む）、マスタ、試算表 | 画面から出せるCSVと同じ（Aと同等） |
| このアプリで増える機能 | — | 登録経路を「推測」でなく事実として表示／明細CSVなしで照合／未処理明細の把握／科目の種類を名前から推定しなくて済む | 取込の手間が減るだけ |
| 権限・同意 | 担当者がCSVを出せれば足りる | 顧問先ごとにアプリ連携の認可が要る。連携アプリ一覧に表示される | 顧問先の了承、freee の規約上の扱いの確認が要る（[v4.5設計](../../docs/v4.5設計_ブラウザ拡張から受信トレイへ_20261013.md)で未確認のまま） |
| 開発負荷 | 済み | 中〜大。`client_secret` を安全に持つ場所（小さなローカルの補助プログラム等）、トークン更新、ページ送り、回数上限への対応が要る。**今の「1ファイルを開くだけ」の形のままでは作れない** | 中。freee の画面変更に追従が要る |
| 運用負荷 | 毎月CSVを出して選ぶ。前月分の出し忘れに注意 | 初回の認可と90日以内の再利用。以後はボタン1つ | 拡張機能の配布・更新、ブラウザごとの設定 |
| 安全性 | 通信なし | freee とそのPCの間だけ通信。トークンの保管が新しい管理対象になる。`read` だけを要求する | 通信なしにできるが、画面操作の自動化は誤動作時の影響が読みにくい |

## 選んだ方式と、次の段階

1. **現在：A（CSV）。** 追加の同意・契約なしに全顧問先で使え、通信しないので安全性の説明が簡単です。レビューの中身（判定・記録・引継ぎ）を先に固める目的にも合います。
2. **次：B（API・読み取り専用）を、まず1社で試す。** レビューの質が上がるのはこの方式だけです（登録経路、口座明細の状態、取引ID）。進める前に確認すること：
   - 事務所のアカウントで顧問先の事業所をAPIから読めるか、顧問先のプランで `journals`・`deals`・`wallet_txns` が使えるか
   - CORS の可否（不可なら、ローカルで動く小さな補助プログラムを置く構成にする）
   - `client_secret` とトークンの保管場所、顧問先への説明文
   - 取り込み口は今のCSVと同じ形（行データ）にそろえ、判定エンジンは変えない。`deal_origin_name`・`rule_matched` は「事実」の欄に出す
3. **C（拡張）は見送り。** 得られるデータがAと同じで、規約上の扱いが未確認のためです。APIを使えない顧問先が多いと分かった場合にだけ、観察型（利用者が自分でCSVを出し、拡張は受け渡すだけ）を再検討します。

日付で結果が変わる判定に使っているのは、インボイス経過措置の控除割合だけです。アプリの詳細画面にも同じ出典を表示します。

|---|---|
| 適格請求書発行事業者以外からの課税仕入れ：2023/10/1〜80%、**2026/10/1〜70%**、2028/10/1〜50%、2030/10/1〜30%、2031/10/1〜なし | [国税庁 令和8年度税制改正特集（インボイス関係）](https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/invoice-review/index.htm)、[No.6498](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shohi/6498.htm)（令和8年4月1日現在法令等） |
